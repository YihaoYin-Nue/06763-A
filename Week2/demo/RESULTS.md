# L3 demo — 实际跑出来的结果

在 koishi 本机跑通，PostgreSQL 16.15，2026-09-02。
数据：Intel Berkeley Lab，54 个 mote，2004-02-28 00:58:46 → 2004-04-03 16:51:34（UTC）。

## 载入

| 指标 | 值 |
|---|---|
| 原始行数 (`data.txt`) | 2,313,682 |
| 清洗后 tidy 行数 `(sensor_id, ts, variable, value)` | **9,119,212** |
| 传感器数 | 54 |
| 解析 + 清洗 + 写 CSV 耗时 | 16.0 s |
| 服务端 `COPY ... FROM 'tidy.csv'` 耗时 | **51.6 s** |
| 外键校验 | ✅ 插入 `sensor_id=999` 被拒：`violates foreign key constraint "readings_sensor_id_fkey"` |

`COPY` 是这里的关键：910 万行 52 秒。同样的数据用逐行 `INSERT` 是"一个下午"级别的差距。
（对照：同一份数据用 notebook 里那种 Python `StringIO` 流式 COPY，我在另一台机器上测是 151 s——
服务端从文件 COPY 快约 3 倍，A2 里值得记一笔。）

## Q3 — 用 `lag()` 定位断档

最大的几个 gap 都是 **1 天 00:31 左右，集中在 2004-03-11 09:36**，
而且 50、22、49、41、36 号几乎同时出现——不是单个 mote 坏了，是一次全网停摆
（供电或网关）。单看 Q2 的计数看不出这件事，`lag()` 把它定位到了具体时刻。

完整前 25 条见 `results/q3_gaps.csv`。

## Q4 — 一小时滚动平均电压

`RANGE BETWEEN interval '1 hour' PRECEDING AND CURRENT ROW`——因为采样不规则，
按时间开窗才诚实，按固定行数开窗是错的。1 号 mote 起始电压 2.700 V，滚动均值平滑地跟着走。

## Q5 — 物理上不可能的读数，以及什么能预测它

| impossible | pct_impossible | pct_of_impossible_below_2v4 |
|---:|---:|---:|
| **391,670** | **17.7%** | **100.0%** |

39 万条温度读数落在室内实验室不可能的区间（<0 °C 或 >50 °C），占 17.7%。
把每条温度读数按 `(sensor_id, ts)` 关联到同一时刻的电压后：**这些坏读数 100% 来自电压已经掉到 2.4 V 以下的 mote。**

不是"大部分"，是全部。电压不是后勤指标，它就是数据质量指标——
这条是整个 demo 最值钱的结论，A2 的 cleaning rules 直接可以写成"voltage < 2.4 的读数一律标为不可信"。

## 索引：同一个范围查询，建索引前后

### notebook 原版（sensor 5，2004-03-15 → 03-16）

| | 计划顶层 | Execution Time |
|---|---|---|
| 无索引 | Parallel Seq Scan，过滤掉 3,039,737 行 × 3 workers | 183.164 ms |
| 有 `(sensor_id, ts)` | Index Only Scan，Heap Fetches: 0 | **0.029 ms** |

6316×。**但是**——回头看 Q2：5 号 mote 3 月 3 日就死了，
所以这个查询在 3/15–3/16 这个窗口里**返回 0 行**。
索引让"空答案"瞬间返回确实是真收益，但这个倍数不能代表典型情况。

### 换一个真有数据的范围（sensor 21，同样窗口，6,916 行）

| | 计划顶层 | Execution Time |
|---|---|---|
| 无索引 | Parallel Seq Scan | 157.668 ms |
| 有 `(sensor_id, ts)` | Bitmap Index Scan → Bitmap Heap Scan（Heap Blocks: exact=79） | **0.792 ms** |

**199×**，而且计划形状也更有说服力：从"扫 910 万行"变成"命中 79 个 heap block"。
A2 要求 report the difference，用这组数比用空结果那组更站得住。

四份完整计划在 `results/explain_{before,after}{,_nonempty}.txt`。

## 磁盘占用（实测）

| 阶段 | 大小 |
|---|---|
| `readings` 堆表 | 631 MB |
| `readings` 含 TOAST/PK | 826 MB |
| 建索引前整库 | 833 MB |
| `(sensor_id, ts)` 索引建好后整库 | **962 MB** |
| 索引合计（PK + 复合索引） | 324 MB |
| 索引构建耗时 | 2.0 s |

外加临时文件：`data.zip` 33 MB、`data.txt` 151 MB、`tidy.csv` 420 MB（灌完可删）。

注意 `pg_database_size` 报的 962 MB 是**逻辑**大小；数据目录实际占 **1.8 GB**，
多出来的主要是 `pg_wal`（批量 COPY 之后攒下的 WAL 段）。做 A2 规划磁盘时按 **2 GB** 算，别按 1 GB。
